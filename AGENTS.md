# Инструкции для AI-агентов в Compound Interest

## Область действия

Эти инструкции действуют для всего репозитория.

Compound Interest — iOS-приложение для расчёта сложного процента. Ограничивайте работу текущими репозиторием и задачей. Не переносите код, продуктовые решения, метрики, учётные данные или клиентскую информацию проекта в другой проект без явного разрешения пользователя.

## Источники истины

Читайте только документы, относящиеся к текущей задаче:

- `README.md` — назначение продукта, структура репозитория, настройка, сборка, CI и общий процесс публикации.
- `docs/project-guidelines.md` — архитектура, SwiftUI, layout, константы, уровни доступа и правила preview.
- `docs/swift-style.md` — стиль Swift-кода.
- `docs/swiftlint-rules.md` — действующая политика SwiftLint.
- `docs/scripts.md` — генерация, lint, Fastlane и поведение скриптов.
- Текущие код и тесты — фактически реализованное поведение.

Документация является источником задуманных правил проекта, а код и тесты — свидетельством текущего поведения. Явно сообщайте о существенных противоречиях между ними, а не выбирайте одну сторону молча.

## Ответственность и делегирование

- Главный агент отвечает за задачу, целостный результат и итоговую проверку. Он может самостоятельно реализовывать изменения.
- Делегируйте только ограниченную работу, которой действительно полезны отдельный контекст, специализация, параллельное выполнение или независимое ревью.
- Каждая делегированная задача должна содержать конкретную цель, релевантный контекст, область владения файлами, ограничения, ожидаемый результат и критерии приёмки.
- При параллельном редактировании области владения файлами не должны пересекаться. Главный агент разрешает конфликты и интегрирует результаты.
- Сохраняйте несвязанные пользовательские изменения в рабочем дереве.

## Границы полномочий

Пользователь утверждает:

- продуктовый scope и приоритет;
- существенное расширение задачи за пределы запроса;
- важные или трудно обратимые архитектурные компромиссы;
- принятие существенного нерешённого риска;
- релизы и другие внешние или разрушительные действия.

В рамках согласованного scope главный агент может самостоятельно принимать обычные технические решения, безопасно редактировать локальные файлы и выполнять проверки.

Если пользователь просит объяснить, диагностировать или провести ревью, изучайте материалы и сообщайте результат без редактирования, пока пользователь также не попросит внести изменения. Никогда не выполняйте push, merge, deploy, загрузку сборки, изменение signing assets, ротацию учётных данных или другие изменения удалённого состояния без явного разрешения пользователя. Явный запрос начать Delivery по GitHub Issue разрешает оркестратору обновлять Project status и checklist, создавать ветку, commit, push и связанный Draft PR. Merge, deploy и релиз требуют отдельного разрешения.

## Риск и ревью

Перед реализацией классифицируйте каждую задачу, изменяющую код:

- **Низкий риск:** документация, узко ограниченная уборка или локальный рефакторинг без изменения поведения и с простой проверкой.
- **Средний риск:** видимое пользователю поведение, локальная бизнес-логика, зависимости или конфигурация сборки с ограниченным радиусом последствий.
- **Высокий риск:** семантика расчётов, округление, хранение или миграция данных, приватность или аналитика, signing, автоматизация релизов, публикация, безопасность, concurrency или широкие архитектурные изменения.

При сомнении выбирайте более высокий уровень риска.

- Изменения низкого риска требуют релевантных автоматических проверок и self-review.
- Изменения среднего и высокого риска требуют независимого ревью перед завершением.
- После замечаний ревью главный агент отвечает за исправления и повторную проверку.

## История задач и долговечные решения

- Используйте GitHub Issue для описания проблемы и критериев приёмки, когда нужна сохраняемая история задачи.
- Используйте pull request для истории реализации, обсуждения ревью и доказательств проверки.
- Используйте GitHub Project для приоритетов, статусов и портфельного представления, а не как историю реализации.
- Добавляйте документ в `docs/decisions/` только для долговечного и неочевидного решения, обоснование и последствия которого будут важны в будущей работе.
- Не создавайте обычные implementation report, QA report или отдельную папку документов для каждой задачи, если Issue, pull request, код и проверки уже сохраняют нужную информацию.

## Проверка

Сначала запускайте самые узкие релевантные проверки и расширяйте их пропорционально риску.

Для изменённых Swift-файлов по возможности запускайте точечный SwiftLint:

```sh
swiftlint lint --config Scripts/swiftlint/.swiftlint.yml --no-cache <changed-swift-files>
```

Для более широких изменений Swift используйте:

```sh
Scripts/swiftlint/swiftlint.sh
```

Wrapper может завершиться успешно, даже если SwiftLint сообщил о нарушениях. Проверяйте его вывод, а не только код завершения.

Запускайте `Scripts/generate.sh` после изменений XcodeGen, SwiftGen, проектного окружения, ресурсов, требующих генерации, или структуры проекта. Не перегенерируйте проект после несвязанных изменений.

Для обычной локальной проверки используйте сборку без подписи:

```sh
xcodebuild \
  -project "Compound Interest.xcodeproj" \
  -scheme "CompoundInterest" \
  -destination "generic/platform=iOS Simulator" \
  CODE_SIGNING_ALLOWED=NO \
  build
```

Запускайте целевые тесты, когда существует подходящий test target. Не называйте пройденными тесты или проверки в симуляторе, которые фактически не запускались.

Не запускайте `Scripts/ci.sh`, Fastlane deploy lanes или TestFlight workflows без явного разрешения пользователя: они могут использовать signing material или внешние сервисы.
