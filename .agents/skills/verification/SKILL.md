# Проверка результата

Подтверждать наблюдаемое поведение и качество доказательствами. Не считать успешную команду, визуальное впечатление или утверждение автора достаточным подтверждением без проверки релевантного результата.

## Границы

- Проверять результат независимо от автора изменения.
- Не редактировать исходный код и тесты во время независимой проверки.
- Не подменять Code Review: не оценивать архитектуру и качество реализации глубже, чем необходимо для выбора проверок и объяснения наблюдаемого сбоя.
- Не запускать deploy, публикацию, signing, Fastlane release lanes, внешние workflow или другие действия, меняющие удалённое состояние, без отдельного разрешения пользователя.
- Следовать `AGENTS.md` и читать только относящиеся к проверке проектные документы.
- Разделять пройденные, проваленные, заблокированные и незапущенные проверки.

## Workflow

### 1. Зафиксировать контракт проверки

Получить или восстановить из задачи:

- критерии приёмки и ожидаемое поведение;
- уровень риска и затронутые сценарии;
- diff или список изменённых файлов;
- заявленные автором проверки;
- ограничения среды и явно исключённые сценарии.

Если критерий нельзя наблюдать или однозначно проверить, отметить это до запуска команд и предложить проверяемую формулировку. Не придумывать отсутствующие требования.

### 2. Составить минимальную матрицу

Для каждого критерия определить:

- способ проверки;
- ожидаемый результат;
- наиболее вероятную регрессию;
- требуемое окружение или данные;
- достаточное доказательство.

Начинать с узких проверок и расширять их пропорционально риску. Для высокого риска включать граничные, ошибочные и регрессионные сценарии, а не только happy path.

### 3. Проверить исходное состояние

- Зафиксировать состояние рабочего дерева до проверки.
- Убедиться, что команды соответствуют текущей задаче и проектным инструкциям.
- Не считать несвязанные пользовательские изменения частью проверяемого результата.
- Выбирать временные или явно разрешённые каталоги для build artifacts.

### 4. Выполнить автоматические проверки

Запустить только релевантные команды из `AGENTS.md`, документации проекта или test target:

- точечный lint для изменённых файлов;
- целевые тесты изменённой логики;
- сборку нужной конфигурации;
- генерацию только когда изменение действительно её требует;
- более широкий набор тестов при соответствующем радиусе последствий.

Проверять не только exit code, но и вывод команды. Не скрывать ошибки, существенные предупреждения, skipped tests или отсутствие ожидаемых тестов.

### 5. Проверить наблюдаемое поведение

- Воспроизвести каждый доступный критерий приёмки.
- Сравнить ожидаемый и фактический результат.
- Проверить состояния до, во время и после пользовательского действия, если поведение зависит от последовательности.
- Для UI использовать симулятор, browser или другой доступный runtime только когда сценарий фактически можно запустить.
- Для расчётов и данных проверять граничные значения, округление, пустые данные и ошибочные входы согласно риску.

Не называть сценарий пройденным по чтению кода или успешной сборке.

### 6. Проверить регрессии

Выбрать ближайшие связанные сценарии, которые могли измениться из-за diff. Не запускать полный набор проверок автоматически, если он не уменьшает конкретный риск.

При сбое:

- повторить его при возможности;
- записать точные шаги, входы и наблюдаемый результат;
- отделить дефект продукта от ограничения среды или нестабильного теста;
- не исправлять код внутри независимого прохода.

### 7. Сформировать заключение

Использовать один статус:

- **Пройдено** — все обязательные доступные проверки подтвердили критерии;
- **Провалено** — есть воспроизводимое несоответствие или обязательная проверка завершилась ошибкой;
- **Частично проверено** — часть результата подтверждена, но остались существенные незапущенные проверки;
- **Заблокировано** — проверка невозможна из-за конкретного ограничения среды, данных или доступа.

Статус «Пройдено» не означает, что Code Review завершён.

## Формат Verification Report

```markdown
# Verification Report

## Заключение
Статус и краткое обоснование.

## Критерии приёмки
Для каждого критерия: способ проверки, ожидаемый результат, фактический результат и статус.

## Выполненные проверки
Точные команды или шаги, окружение и результат.

## Сбои
Воспроизводимые шаги, доказательства и влияние. Если сбоев нет — явно указать это.

## Непроверенное и ограничения
Что не запускалось, почему и какой риск остаётся.

## Уверенность
Высокая, средняя или низкая с кратким объяснением.
```
