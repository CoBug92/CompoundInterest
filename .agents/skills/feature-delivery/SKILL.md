# Реализация функции

Доставлять минимальное целостное изменение в согласованном scope. Главный агент отвечает за интеграцию, проверку и итоговый результат, даже если часть работы делегирована.

## Основные правила

- Считать явный запрос пользователя на реализацию разрешением на безопасные локальные изменения в пределах запроса.
- Если пользователь явно просит начать Delivery по GitHub Issue, считать это разрешением на стандартный lifecycle задачи: обновлять её Project status и checklist, создать ветку, commit, push и связанный Draft PR. Не считать это разрешением на merge, deploy или релиз.
- Не требовать отдельного агента для каждой роли. Подключать специалистов только при ожидаемой пользе.
- Разделять фактически выполненные проверки, предположения и непроверенные утверждения.
- Сохранять несвязанные пользовательские изменения и не переписывать чужую работу.
- Следовать `AGENTS.md` и загружать только релевантную проектную документацию.

## Workflow

### 1. Подтвердить готовность к Delivery

Определить:

- какое поведение должно измениться;
- для кого оно меняется;
- критерии приёмки;
- ограничения и non-goals;
- связанные Issue, Discovery Brief или решения;
- что пользователь фактически разрешил изменить.

Если критерии не указаны, сформулировать проверяемую рабочую версию и явно показать её пользователю. Задать вопрос до реализации только тогда, когда разумные трактовки ведут к существенно разным результатам или рискам.

Не начинать реализацию, если пользователь просит только обсудить, оценить или спланировать функцию.

### 2. Классифицировать риск

Использовать уровни из `AGENTS.md`: низкий, средний или высокий. Кратко обосновать уровень по изменяемому поведению, радиусу последствий, обратимости и качеству доступной проверки.

При сомнении выбирать более высокий уровень.

### 3. Исследовать минимально необходимый контекст

- Найти текущий путь выполнения и владельцев поведения.
- Прочитать только релевантные документы, код и тесты.
- Проверить состояние рабочего дерева и сохранить несвязанные изменения.
- Выявить затрагиваемые интерфейсы, данные, генерацию, локализацию и CI.
- Сообщить о конфликте документации и фактического поведения.

Если Delivery связан с GitHub Issue и доступен GitHub Project:

- главный агент переводит Issue в `In Progress` до реализации;
- запоминает идентификаторы Project item и полей, не поручая управление статусами специалистам;
- при недоступной интеграции явно сообщает об этом, не имитирует успешное обновление.

Для узкой задачи провести исследование главному агенту. Подключить Explorer, когда поиск можно ограничить конкретным вопросом и отдельный контекст уменьшит шум.

### 4. Выбрать маршрут

#### Низкий риск

```text
Главный агент → реализация → автоматические проверки → self-review
```

#### Средний риск

```text
Исследование → план → реализация → Verifier → Code Reviewer → исправления → повторная проверка
```

#### Высокий риск

```text
Исследование → план и согласование существенных компромиссов → ограниченная реализация → Verifier → Code Reviewer → исправления → повторная проверка → решение пользователя о принятии риска
```

Не добавлять этап, если он не уменьшает конкретный риск или неопределённость.

### 5. Делегировать ограниченную работу

По умолчанию поручать изменение кода Engineer на Terra medium. Главный агент интегрирует результат и отвечает за workflow. Самостоятельно реализовывать только тривиальную задачу низкого риска, недоступность Engineer или узкое исправление finding; кратко фиксировать причину.

Использовать встроенных специалистов:

- Explorer на Terra low — для ограниченного чтения и поиска по кодовой базе;
- Worker на Terra medium — для реализации с чёткими границами;
- Sol medium — при неоднозначной, межмодульной или неудавшейся на Terra задаче; Sol high только для подтверждённого высокого риска, который Terra не разрешила.

Передавать каждому агенту:

- конкретную цель;
- релевантный контекст;
- разрешённые файлы или область ответственности;
- ограничения и запрещённые изменения;
- ожидаемый результат;
- критерии приёмки и обязательные проверки.

Не поручать нескольким агентам параллельно редактировать пересекающиеся файлы. Не повторять один и тот же неудачный запрос Terra без новых данных; передавать Sol факты и причину неудачи.

### 6. Реализовать изменение

- Внести минимальное целостное изменение, достаточное для критериев приёмки.
- Соблюдать проектную архитектуру и правила кода.
- Добавить или обновить тесты для изменяемой логики, когда test target и подходящий уровень тестирования существуют.
- Не добавлять зависимость, инфраструктуру или документацию без необходимости для задачи.
- Не выполнять несвязанный рефакторинг.
- Обновить пользовательскую документацию только при изменении публичного поведения или процесса.

Главному агенту проверять и интегрировать результаты Worker, а не принимать их как доказанно корректные.

### 7. Проверить результат

- Запустить самые узкие релевантные проверки из `AGENTS.md`.
- Расширить проверки пропорционально риску.
- Проверить критерии приёмки и регрессионные сценарии.
- Использовать Verifier для среднего и высокого риска, когда он доступен.
- Зафиксировать команды, результаты и ограничения среды.

Главному агенту не дублировать полный независимый прогон: до Verifier выполнять только минимальный smoke-check, необходимый для передачи проверяемого результата. После отчёта Verifier обновить только подтверждённые acceptance checkboxes в Issue; непройденные и непроверенные пункты оставить открытыми.

Не называть пройденными тесты, сборку или поведенческие сценарии, которые не запускались. Не подменять проверку успешным завершением команды, если её вывод содержит ошибки или предупреждения, требующие оценки.

### 8. Провести ревью

- Для низкого риска выполнить self-review diff и проверить отсутствие лишних изменений.
- Для среднего и высокого риска перед завершением использовать независимого Code Reviewer.
- Передать reviewer критерии приёмки, риск, diff и доказательства проверки.
- Главному агенту исправить существенные findings и повторить затронутые проверки.
- Не закрывать задачу с нерешённым существенным finding без решения пользователя.

Если обязательный reviewer недоступен, обозначить задачу как ожидающую ревью, а не как завершённую.

### 9. Завершить Delivery

Для Delivery по GitHub Issue главный агент:

1. создаёт связанную ветку и включает только изменения задачи;
2. создаёт commit и push после успешных обязательных проверок;
3. создаёт Draft PR с `Closes #<issue>` и доказательствами проверки;
4. переводит Project item в `Code Review` после создания PR;
5. переводит в `Done` и закрывает Issue только после merge либо по явному правилу Project; не поручает это Verifier или Code Reviewer.

Если грязное рабочее дерево не позволяет безопасно отделить изменения, остановиться перед commit и запросить решение пользователя.

Считать Delivery завершённым, когда:

- критерии приёмки выполнены;
- код и необходимые тесты изменены согласованно;
- релевантные проверки пройдены либо ограничения явно приняты пользователем;
- обязательное независимое ревью завершено;
- существенные findings исправлены или явно приняты пользователем;
- отсутствуют несвязанные изменения, внесённые текущей задачей.

Вернуть Delivery Summary в диалоге или pull request. Не создавать отдельный отчётный файл автоматически.

## Формат Delivery Summary

```markdown
## Результат
Что изменено и какое поведение теперь обеспечено.

## Риск
Уровень и краткое обоснование.

## Проверка
Фактически выполненные команды и поведенческие проверки с результатами.

## Ревью
Self-review или независимое ревью; существенные findings и их статус.

## Ограничения и остаточные риски
Что не проверено, почему и какое решение требуется.
```

Не создавать Issue, pull request, commit или push без разрешения. Явный запрос начать Delivery по связанному Issue является таким разрешением для стандартного lifecycle выше. Merge и релиз всегда требуют отдельного разрешения.
